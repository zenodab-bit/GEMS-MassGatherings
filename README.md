# GEMS-MassGatherings

An extension of the [GEMS](https://github.com/IMMIDD/GEMS) epidemic simulator that adds mass gathering events (festivals, concerts, sport) on top of the normal GEMS settings.

Event contacts are extra contacts: GEMS calculates each person's contacts in the normal settings (household, office, school, etc.) without considering their participation in events, and the event contacts are added on top. Events run through GEMS's global setting. GEMS puts the entire population in it, but the code narrows it down each day to only that day's event attendees (nobody on days without events), so its cost depends on event sizes rather than population size. It has not been tested on populations larger than Saalekreis.

## Setup (once per machine)

1. Install Julia 1.12 (the project was built with 1.12.5): https://julialang.org/downloads
2. Download the code and enter the folder (or download the ZIP from the GitHub page, after selecting the `multi-event-fixes` branch):
   ```
   git clone -b multi-event-fixes https://github.com/zenodab-bit/GEMS-MassGatherings.git
   cd GEMS-MassGatherings
   ```
3. Install the packages:
   ```
   julia setup.jl
   ```
   This installs the exact package versions recorded in `Manifest.toml`, GEMS included. Do not run `Pkg.update()`: it moves GEMS and the other packages to their newest versions, which may not work with this code.
4. Run a simulation, from the `GEMS-MassGatherings` folder:
   ```
   julia Concert_Project/2_Interface.jl
   ```
   Results are saved in the project's `Results/` folder (next to `Concert_Project/`), wherever Julia was started from.

## Running a simulation

1. Configure the simulation in `Concert_Project/1_UserConfig.jl` (see [Configuring events](#configuring-events) below).
2. If needed, change the settings in `Concert_Project/2_Interface.jl`:
   - `n_simulations`: how many replicates to run.
   - `run_validation`: whether to run the checks in `7_Validation.jl`.
   - `population_file`: the base population, Saalekreis by default. Any `.jld2` file holding a table under `"data"` works, with at least `id`, `age`, `sex` (1 or 2) and the GEMS setting ids (`household`, and optionally `office`, `schoolclass`, `municipality`), like the GEMS population files.
   - `settings_file`: the matching GEMS settings file, or `nothing` if the population has none. It adds e.g. household coordinates, region codes and the larger groupings (schools, workplaces). GEMS only reads a settings file when the population is given as a file, so with a settings file `2_Interface.jl` writes the prepared population (with the event columns) to a temporary file, checks that the event columns read back unchanged, passes that file to GEMS and deletes it after the runs. This makes runs noticeably slower (each replicate reads the file back, and the extra settings are simulated too). With `nothing`, the population is passed to GEMS directly, which is faster but leaves out the coordinates, region codes and larger groupings.
3. Run `2_Interface.jl`, as in step 4 of the setup.

### Quick test

After changing the code, run `test.jl` to check that everything still works end to end:
```
julia Concert_Project/test.jl
```
It runs the same steps as `2_Interface.jl`, but on a synthetic population of 5,000 people generated by GEMS, with a 60-day simulation and its own small event config written inside the file (it replaces `1_UserConfig.jl`). That config uses most features (several categories and sections, both section modes, core, loyalty, cross-section contacts), so a change that breaks one of them shows up. The results are not meant to be realistic and are saved in `Results/test_...`. The steps in `test.jl` copy `2_Interface.jl`, so keep the two in step when `2_Interface.jl` changes.

**Reproducibility.** There are two seeds:

1. `seed` in the TOML sets the setup: the events, each person's transmission probability and who attends what. The same seed gives the same setup every time. Each of the three steps has its own random stream derived from `seed`, so changing one doesn't reshuffle the others: changing an event's size or `n_draws` leaves everyone's transmission probability unchanged, and changing `loyalty` or `core` leaves the events and transmission probabilities unchanged.
2. `gems_seed` in `1_UserConfig.jl` sets the epidemic itself (initial infections, contacts, infections, disease course). With `gems_seed = nothing` (the default), every run uses a new random seed, so results differ between runs. The seed used is printed and saved at the top of `multievent_analysis.txt`. To repeat a run exactly, set `gems_seed` to that value and use the same number of Julia threads as that run (also saved there).

Replicates within one run always differ from each other: GEMS derives a separate seed for each one from `gems_seed`.

**Event dates.** GEMS simulates days 0 to `StopCriterion.limit` − 1 (in the TOML), so with `limit = 120` the last simulated day is 119. Every event's date must be on or before that day. If a category's `date_range` allows a later date, `2_Interface.jl` warns but still runs. Results for that event will be inaccurate, since the simulation ends before that day is reached.

**Reading validation output.** The Epidemic State Z-scores are sanity checks, not formal tests: the expected values are rough approximations, so only very large Z-scores deserve a closer look. Observed values are means over replicates, so each Z-score uses the spread of that mean (one run's std divided by √(number of replicates)). A Z-score of "n/a" means there's only one simulation replicate, so there's no variance to compare against; it is not an error. The "Infected" row is the exception: its std comes from a binomial model, not from replicates, so it always has a Z-score. That std is a lower bound (it ignores variation in contacts and infectiousness), so treat large Z-scores there with care.

### Rerunning a run

Every run folder has a `run_info/` folder with what's needed to repeat that run:

- copies of the files it was configured with: `1_UserConfig.jl`, `2_Interface.jl` and the TOML (for a `test.jl` run: `test.jl` and the TOML);
- `run_info.toml`: the setup seed, the GEMS seed actually used, the number of replicates, the population and settings files (by path, not copied), the Julia version and thread count, and the code version (git commit and branch);
- `uncommitted_changes.diff`, only if the code had changes not yet committed when the run started (new files never added to git are not included).

To rerun:

1. Check out the saved commit: `git checkout <git_commit>`. If there is an `uncommitted_changes.diff`, apply it: `git apply <run folder>/run_info/uncommitted_changes.diff`.
2. Copy the saved config files back into `Concert_Project/`.
3. In `1_UserConfig.jl` (or `test.jl`), set `gems_seed` to the `gems_seed` in `run_info.toml`. The saved copy has whatever was there when the run started, usually `nothing`.
4. Make sure the population and settings files at the saved paths are the same ones, and run with the same number of threads (`julia -t <threads> ...`).

## Files

All code is in `Concert_Project/`:

| File | Purpose |
|---|---|
| `0_Helpers.jl` | Structs and helper functions used by the other files. |
| `1_UserConfig.jl` | Transmission probability and the event definitions. |
| `2_Interface.jl` | Links everything together and runs the simulations. |
| `3_Population.jl` | Creates the events and assigns the population to them. |
| `4_Contacts.jl` | Contact sampling for the whole simulation: normal settings (household, office, etc.) and events each use their own logic. |
| `5_Transmission.jl` | Transmission function for the whole simulation, with the same split as above. |
| `6_Analysis.jl` | Output: text metrics and plots. |
| `7_Validation.jl` | Checks and extra metrics to confirm the code works correctly. |
| `config_concert_covid.toml` | The standard GEMS configuration file. |
| `test.jl` | Quick end-to-end check on a small synthetic population, with its own small config. See [Quick test](#quick-test). |

In the TOML, the transmission function's `parameters` table is empty on purpose: GEMS requires the table, but transmission uses each person's own probability, set in `1_UserConfig.jl`. Likewise, the GlobalSetting's contact method has no parameters, since event contact rates are set per section in `1_UserConfig.jl`.

## Configuring events

In `1_UserConfig.jl` you first set `transmission_dist`, the distribution each person's transmission probability (chance of infecting a contact) is drawn from, once at the start. Any distribution from Distributions.jl works; values are kept within [0, 1]. Examples:

```julia
transmission_dist = Gamma(gamma_params(0.3, 0.1)...)   # by mean and std (the default)
transmission_dist = Beta(beta_params(0.3, 0.1)...)     # by mean and std, always within [0, 1]
transmission_dist = Dirac(0.3)                          # the same for everyone
```

Then you create categories of events. Each category has these fields:

- **`id`**: unique id used for internal processing. `validate_config` stops with an error if two categories share an id.
- **`name`**: makes the outputs easier to read. Should also be unique, since some output filenames are built from it, and a collision overwrites one category's output with another's.
- **`date_range`**: the days on which events of this category can happen.
  - Events of the same category cannot happen on the same day. The code picks different dates, but the range needs enough days.
  - Different categories can land on the same date by coincidence. In that case all events of that date are filled together: core first, then loyalty, then random. So a category can never take another's core members, and its random fill can't take another's loyal attendees.
  - A person can attend events from more than one category on different days. Being core or loyal to one category doesn't exclude someone from being randomly drawn into another's events.
- **`sections`**: at least one per category. This is where the size and number of contacts are set. Multiple sections must have unique ids (`validate_config` stops with an error otherwise), and every event of the category has all its sections.
- **`n_draws`**: how many times the category recurs. The total number of events created is `n_draws` times the number of sections, not `n_draws` itself. A negative value is an error; 0 gives a warning and creates no events for that category.
- **`min_age`, `max_age`**: minimum and maximum age of attendees. `age_boundaries` (see below) are shared across categories, but since the min and max age filter who is eligible first, the same boundary can cover a different real age range per category.
- **`age_weights`**: the age distribution of attendees, within the min and max ages. These are weights and don't have to sum to 1, so the real distribution at the event may differ slightly.
- **`sex_weights`**: the sex distribution of attendees. Also weights, with the same caveat.
- **`core`**: the fraction of each draw's attendees who attend every draw of the category.
  - It is calculated on the smallest draw generated (all sections together), so all core members always fit. With `section_mode = :section` it is calculated on each section's smallest size instead, so every home section fits. This gives a slightly smaller core.
  - Core members are picked following the demographic weights.
  - A person can be core for at most one category.
  - With several sections, placement depends on `section_mode`.
- **`loyalty`**: the fraction of the remaining non-core spots reserved for people who already attended at least one non-core event of the category. This pool only grows and never expires. Selection follows the demographic weights; attending more times doesn't give extra weight. With several sections, placement depends on `section_mode`.
- **`cross_section_mean_contacts`**, **`cross_section_std_contacts`**: contacts a person has with people in other sections of the same event. The same value applies to all sections, and these contacts come on top of the within-section ones.
- **`section_mode`**: where core and loyal members go when there are several sections. `:event` (the default) places them in a random section at every draw, in proportion to section size. `:section` gives core members a fixed home section, and loyal attendees go back to their last section.

Core members are picked once per category, before any of its events are processed. The same core then attends every event of the category, from the first one on. Events are filled date by date: core of every event, then loyalty of every event, then random fill of every event. Anyone filled by loyalty or random fill becomes loyalty-eligible for that category's later events.

`validate_config` runs automatically once `event_config` is built. It catches common mistakes like wrong-length weight lists, inverted ranges, `core` outside [0, 1], negative `n_draws`, and duplicate category or section ids. Not everything is checked; see its comments in `0_Helpers.jl` for the full list.

Finally, `event_config` lists which categories are included in the simulation, so categories can easily be switched on or off for testing. It also holds `age_boundaries`, used to group ages the same way for all events, and `age_dist` and `sex_dist`, used for any category without its own `age_weights` or `sex_weights`.

## What happens during a run

`2_Interface.jl` loads `0_Helpers.jl` and `1_UserConfig.jl`, then the rest of the code.

**3_Population** turns the categories into actual events (each with a date and a size), prepares the population chosen in `2_Interface.jl` (`population_file`), and assigns people to every event following the rules above. Nothing here needs to be configured.

Each person's transmission probability is drawn once, at the very start, from `transmission_dist` in `1_UserConfig.jl`, kept within [0, 1]. It never changes afterward, regardless of which events that person attends. A few fields are added to every person so the rest of the code knows who attended what:

- `category_ids`, `draw_ids`, `section_ids`: which category, draw and section they attended, one entry per event attended.
- `event_dates`: the date of each event attended.
- `mean_event_contacts`, `std_event_contacts`: their within-section contact rate at each event.
- `cross_section_mean_contacts`, `cross_section_std_contacts`: the same, for contacts with people in other sections of the same event.
- `transmission_prob`: fixed at the start, not tied to any event.

**4_Contacts** defines how many contacts a person has in every setting, both normal ones and events. For events it handles both within-section and cross-section contacts. Attendance is fixed before the simulation, but on the event day people who are dead, severely ill or in hospital don't go: they get no event contacts and nobody can draw them as a contact. People with milder symptoms, or none yet, still go. In the per-event results, these people are counted in the **Absent** row; all other rows (susceptible, infectious, exposed, recovered) only count attendees who were actually there. It also contains `daily_global_setting!`, which `2_Interface.jl` passes to GEMS as the batch's `setup`: before each simulation starts, it builds one list of attendees per event day and makes GEMS swap in the right list at the end of every day. It also stops with an error if the event attendances GEMS holds don't add up to those in the population table, since missing event columns would otherwise fail silently (no event contacts at all).

**5_Transmission** decides whether a contact results in an infection. Normal settings use the infecter's own `transmission_prob`. For events it also checks that the infecter and the infected attended the same event (any section).

`2_Interface.jl` then samples the events, prepares and assigns the population, and runs the GEMS simulation.

**6_Analysis** runs automatically afterwards and produces the text metrics and the plots (epidemic curves, cases by setting, per-event SEIR bars, infected boxplots), saved to the `Results` folder. Per event, the text output gives two rates: the share of all attendees infected at the event, and the attack rate among susceptible attendees (those who could still be infected when they arrived), averaged over replicates. The global section also gives the offspring dispersion k: how unevenly onward infections are spread across infected people (lower k means more superspreading). People infected near the end of the simulation are left out of k, because the simulation ends before they finish infecting others. How many days are left out is measured from each run itself: it's the time within which 95% of infected people stopped being able to infect (until recovery, death or hospital admission), so it follows the pathogen settings in the TOML. The output says how many days that was.

**7_Validation** runs if `run_validation` is `true`. It checks the outcomes (assignment counts, compartment totals, demographics, epidemic state) against what's expected. Not required for a normal run, but useful to catch mistakes. Its output is shown on screen and saved as `validation.txt`.

### What a run folder contains

| File | Content |
|---|---|
| `multievent_analysis.txt` | Seeds, global metrics (infections, attack rate, R0, offspring k) and, per event, each compartment summarised across replicates (mean, std, min, quartiles, max) plus the two rates |
| `validation.txt` | The validation output (only if `run_validation` is `true`) |
| `events.csv` | One row per event: id, name, category, draw, section, date, size, contact rates |
| `event_results.csv` | One row per replicate and event, with every compartment count before summarising |
| `attendance.jld2` | Who was assigned to each event (`"attendees"`: event id => person ids) and each category's core group (`"core_groups"`: category id => person ids) |
| `*.png` | The plots |
| `run_info/` | Everything needed to rerun the run (see [Rerunning a run](#rerunning-a-run)) |

The full infection logs are not saved (about 150 MB per replicate for Saalekreis).
