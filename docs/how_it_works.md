# How it works

## The idea

The project extends the [GEMS](https://github.com/IMMIDD/GEMS) epidemic simulator with mass gathering events. Event contacts are extra contacts: GEMS calculates each person's contacts in the normal settings (household, office, school, etc.) without considering their participation in events, and the event contacts are added on top. Events run through GEMS's GlobalSetting. GEMS puts the entire population in it, but the code narrows it down each day to only that day's event attendees (nobody on days without events), so its cost depends on event sizes rather than population size. It has not been tested on populations larger than Saalekreis (about 435,000 people).

## The code

The code is a Julia package, `MassGatherings`, in `src/`. `run.jl` loads it with `using MassGatherings`; the module file `src/MassGatherings.jl` lists the files below (loaded in this order) and what users may call (its `export` list). Everything else is internal, reachable as `MassGatherings.name` if needed.

| File | Contents |
|---|---|
| `src/utils.jl` | Distributions (negative binomial, gamma, beta), age groups, plot colours, table formatting |
| `src/config.jl` | The configuration structs (`EventSection`, `Category`, `Venue`, `Stage`, `StagedCategory`, `EventConfig`), `Event`, and `validate_config` |
| `src/events.jl` | Drawing the events: dates and sizes for every draw (and every venue of every stage) |
| `src/attendance.jl` | Preparing the population (event columns, `transmission_prob`) and assigning attendees |
| `src/contacts.jl` | Contacts in the normal settings and at events; the daily GlobalSetting lists and the passes per stage |
| `src/transmission.jl` | Transmission |
| `src/results.jl` | Per-event counts, their summary over replicates, attack rates, offspring dispersion, saving |
| `src/scenario.jl` | `run_scenario`: one scenario from start to finish; the setup's random streams, the population, the GEMS runs |
| `src/comparison.jl` | `run_comparison` and the comparison with and without events |
| `src/sweeps.jl` | `run_sweep`, `with_date`, `with_date_range` and the sweep summary |
| `src/analysis.jl` | Text metrics and plots |
| `src/validation.jl` | The checks of a finished run (see [Validation](validation.md)) |

Since the code is a package, it is compiled once and cached (the first start after a change in `src/` takes about 30 s longer). Changing a struct in `src/config.jl` needs a fresh Julia session; running `julia run.jl` always starts one.

## What happens during a run

`run_scenario` goes through these steps, in order. `run_comparison` and `run_sweep` call it for each of their runs, and `test/test.jl` calls it too, so the steps exist in one place only. Each call starts from a fresh copy of the population and recreates the setup's random streams from the setup seed, so calling it twice in one Julia session with the same seeds gives the same events, attendees and results.

**1. Events** (`src/events.jl`): the categories become actual events, each with a date and a size; for staged categories, one event per venue of every stage.

**2. Population and attendance** (`src/attendance.jl`): the population is the one passed in (`population_file` in `run.jl`), or a synthetic one generated by GEMS. Each person's transmission probability is drawn once, from `transmission_dist`, kept within [0, 1], and never changes afterwards. People are then assigned to every event following the rules in [Configuring events](events.md). A few fields are added to every person so the rest of the code knows who attended what:

- `category_ids`, `draw_ids`, `section_ids`, `stage_ids`: which category, draw, section (or venue) and stage they attended, one entry per event attended;
- `event_dates`: the date of each event attended;
- `mean_event_contacts`, `std_event_contacts`: their contact rate at each event;
- `cross_section_mean_contacts`, `cross_section_std_contacts`: the same, for contacts with people in other sections of the same event;
- `transmission_prob`.

GEMS copies these onto its own individuals.

**3. Contacts** (`src/contacts.jl`): how many contacts a person has in every setting, both normal ones and events. At events, an infectious attendee meets a number of different people in their own section or venue (drawn with its mean and std, capped at the number present), plus cross-section contacts if set. Attendance is fixed before the simulation, but on the event day people who are dead, severely ill or in hospital don't go: they get no event contacts and nobody can draw them as a contact. People with milder symptoms, or none yet, still go.

`daily_global_setting!`, which `run_scenario` passes to GEMS as the batch's `setup`, builds one list of attendees per event day before each simulation starts, and makes GEMS swap in the right list at the end of every day. It stops with an error if the event attendances GEMS holds don't add up to those in the population table, since missing event columns would otherwise fail silently. For the run without events (see [Experiments](experiments.md)), it leaves the list empty on every day.

With staged categories, each stage gets its own pass: GEMS's own pass of the day holds the normal events and every staged category's first stage; at the end of the day (still the same day), each further stage is put in the GlobalSetting and GEMS's infection step runs once more, and who gets infected in which pass is recorded. The order of the passes doesn't matter for who can infect whom, since people infected today only become infectious days later.

**4. Transmission** (`src/transmission.jl`): in every setting, events included, a contact infects with the infecter's own `transmission_prob`, unless the contact has already recovered (they are then immune). Who meets whom at events is decided entirely in the contacts, so there's no separate "same event" check; the Infected row of the validation tests that event contacts follow the rules.

**5. GEMS runs** the replicates: as one batch, or one by one when replicates have their own setup, with branching, picked histories or staged categories.

**6. Results** (`src/results.jl`): for every event and replicate, each attendee is classified as of the event day: absent (dead, severe or hospitalised that day), susceptible, infectious, exposed, recovered, infected the same day elsewhere, or infected at the event. These counts are summarised over replicates and saved, with everything needed to rerun the run.

**7. Analysis** (`src/analysis.jl`): the text metrics and the plots. Per event, the text output gives two rates, averaged over replicates: the share of attendees present who were infected at the event, and the attack rate among susceptible attendees (those present who could still be infected when they arrived). The global section also gives the offspring dispersion k: how unevenly onward infections are spread across infected people (lower k means more superspreading). People infected near the end of the simulation are left out of k, because the simulation ends before they finish infecting others; how many days are left out is measured from each run (the time within which 95% of infected people stopped being able to infect), and the output says how many.

**8. Validation** (`src/validation.jl`), if `run_validation` is `true`: see [Validation](validation.md).

## What a run folder contains

| File | Content |
|---|---|
| `multievent_analysis.txt` | Seeds, global metrics (infections, attack rate, R0, offspring k) and, per event, each compartment summarised across replicates (mean, std, min, quartiles, max) plus the two rates. With staged categories, also the attendees present and infected per stage, per draw and over all draws. |
| `validation.txt` | The validation output (only if `run_validation` is `true`) |
| `events.csv` | One row per event: id, name, category, draw, section, date, size, contact rates. With staged categories, one row per venue, with a `stage_id` column (the venue's number is in `section_id`). |
| `event_results.csv` | One row per replicate and event, with every compartment count before summarising. With branching or picked histories, also `history` and `future` columns. |
| `attendance.jld2` | Who was assigned to each event (`"attendees"`: event id => person ids) and each category's core group (`"core_groups"`: category id => person ids). With `vary_per_replicate` set, both are a list with one entry per replicate. |
| `epidemic_overview.png`, `cases_by_setting.png`, `infected_boxplot.png`, `infected_by_section.png`, `seir_<event>.png` | The plots: epidemic curves, daily cases by setting, infected at events, per section or venue over draws, and one SEIR bar chart per event |
| `run_info/` | Everything needed to rerun the run (see [Reproducibility](reproducibility.md#rerunning-a-run)) |

The full infection logs are not saved (about 150 MB per replicate for Saalekreis).

## Populations

`run_scenario` takes a population as a `.jld2` file holding a table under `"data"`, as a table (DataFrame), or `nothing` for a synthetic population generated by GEMS. A population needs at least `id`, `age`, `sex` (1 or 2) and the GEMS setting ids (`household`, and optionally `office`, `schoolclass`, `municipality`), like the GEMS population files.

The synthetic population is made with GEMS's generator, whose settings are in `synthetic` (`n`, `avg_household_size`, `avg_office_size`, `avg_school_size`), from the setup seed's own random stream, so the same seed gives the same population. GEMS calls these populations non-representative: they have households, offices and school classes with realistic ages, but no municipalities, and aren't based on census data. They're for trying things out and for tests.

A **settings file** (`settings_file`) adds what the population file doesn't hold, e.g. household coordinates, region codes and the larger groupings (schools, workplaces). GEMS only reads a settings file when the population is given as a file, so with a settings file `run_scenario` writes the prepared population (with the event columns) to a temporary file, checks that the event columns read back unchanged, passes that file to GEMS and deletes it after the runs. This makes runs noticeably slower (each replicate reads the file back, and the extra settings are simulated too). Without one, the population is passed to GEMS directly.
